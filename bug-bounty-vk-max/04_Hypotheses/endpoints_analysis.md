# Анализ эндпоинтов бизнес-версии MAX

## 1. `GET /self/api/v1/organization` (Строка 43)
*   **Что делает**: Возвращает данные текущей организации (ИНН, ФИО, статус, `org_id`).
*   **Тест на IDOR**: Добавление параметров `?id=9522951` или `?org_id=9522951` к запросу.
*   **Результат**: Сервер возвращает `200 OK`, но игнорирует параметры и отдает данные **текущей** организации (из сессии).
*   **Вывод**: Эндпоинт защищен от IDOR через параметры URL. Права берутся из токена/сессии.

## 2. `POST /method/execute` (Строка 30)
*   **Что делает**: Универсальный шлюз для выполнения кода (VK API style).
*   **Тест**: Замена оригинального кода на `return API.organizations.getById({org_id: 9522951});` с передачей куки `domain_sid`.
*   **Результат**: Ошибка `error_code: 5` (access_token has expired).
*   **Вывод**: Шлюз требует валидный `access_token` (или специфический `silent_token`), а не просто куку сессии. Кука `domain_sid` не подходит. 

## 3. `GET /self/api/v1/permissions` (Строка 44)
*   **Что делает**: Возвращает права доступа для организации (фильтр по `organisation`).
*   **Тест**: Подстановка ID `9522951` и других.
*   **Результат**: `400 Bad Request` с сообщением `wrong filter`.
*   **Вывод**: Эндпоинт жестко валидирует структуру фильтра. ID `9522951` не подходит для этого эндпоинта (возможно, это ID из другого контура).

## 5. `GET /self/api/v1/organizations` (Строка 41)
*   **Что делает**: Возвращает список организаций пользователя.
*   **Результат**: 200 OK, возвращает только одну (текущую) организацию (`14387249`).
*   **Вывод**: Эндпоинт защищен от IDOR (не отдает чужие организации).

## 6. `GET /authorize?redirect_uri=...` (Строка 15)
*   **Тест**: Подстановка `redirect_uri=https://evil.com` и XSS-пейлоада в `redirect_uri`.
*   **Результат**: Сервер возвращает `200 OK` (не редиректит). В ответе XSS не найден (символы экранированы).
*   **Вывод**: Сервер проверяет `redirect_uri` по белому списку (Open Redirect не подтвержден). XSS в этом параметре отсутствует.
