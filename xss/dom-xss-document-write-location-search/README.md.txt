# DOM XSS в document.write (источник: location.search)

**Платформа:** PortSwigger Web Security Academy
**Лаба:** DOM XSS in document.write sink using source location.search
**Уровень:** Apprentice
**Статус:** ✅ Solved

## 🎯 Цель
Найти и подтвердить DOM-based XSS в функционале поиска. Лаба использует клиентский JavaScript с sink `document.write()`, данные для которого берутся из `location.search`. Требовалось выполнить атаку, вызывающую `alert()`.

## 🔍 Разведка и анализ
1.  **Точка входа (Source):** `location.search` — всё содержимое query-строки URL (параметр `search`), полностью контролируется пользователем.
2.  **Точка выхода (Sink):** функция `document.write()` в клиентском скрипте — она склеивает HTML прямо в браузере, без участия сервера.
3.  **Контекст:** значение из query-строки вставляется внутрь **атрибута** `src` тега `<img>` без какого-либо экранирования.

## 🧪 Процесс эксплуатации (Walkthrough)
1.  Ввёл в поиск случайную строку-маркер `zzzTEST123`, открыл DevTools (Inspect) и увидел, что маркер оказался внутри атрибута: `<img src="/?searchResults=zzzTEST123">`.
2.  Сформулировал payload, разрывающий атрибут и открывающий собственный тег:
    ```html
    "><svg onload=alert(1)>
    ```
3.  Вставил payload в поле поиска и нажал **Search**.
4.  Кавычка `"` закрыла атрибут `src` раньше времени, символ `>` закрыл тег `<img>`, и браузер собрал из склейки новый тег `<svg onload=alert(1)>`.
5.  Скрипт исполнился — всплывающее окно с `1`, лаборатория помечена решённой.

## 🛡️ Причина уязвимости (Root Cause)
Клиентский скрипт принимает данные из `location.search` и передаёт их в `document.write()` **без санитизации и контекстного кодирования**. Это **DOM-based** уязвимость: payload не отправляется на сервер и не возвращается в ответе, поэтому в HTTP-логах Burp его не видно — весь путь от source до sink происходит внутри браузера.

## 🛠️ Рекомендации по исправлению
1.  **Отказаться от `document.write`** как от небезопасного API; для вставки данных использовать безопасные методы DOM (`textContent`) или проверенные библиотеки санитизации (DOMPurify).
2.  **Контекстно-зависимое кодирование:** HTML-энкодинг при вставке в разметку, JS-энкодинг при вставке в исполняемый код, URL-энкодинг для атрибутов вроде `src`/`href`.
3.  **Content Security Policy (CSP):** ограничение `script-src` снижает ущерб даже при наличии инъекции.

*   Понял ключевое отличие **DOM XSS** от Reflected: уязвимость живёт в клиентском JS, сервер остаётся «чистым», и перехват HTTP-трафика не покажет payload.
*   Освоил **маркер-метод**: уникальная строка → поиск в Elements → определение контекста посадки (атрибут / текст / JS-строка) → подбор payload под контекст.
