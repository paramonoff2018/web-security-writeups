# AF Bypass — Detection Mismatch

## Что ищем
Несоответствие между фактической обработкой трафика и отображением в интерфейсе:
- **атака доходит до тестового backend**, но в консоли отображается как **заблокированная**
- **атака доходит до тестового backend**, но в консоли **отсутствует** в событиях
- **атака доходит до тестового backend**, но в консоли помечена как **неопасная**

## ⚠️ Это самая «вкусная» категория для PT
Именно здесь платят за **mismatch**, даже если сам payload не «новый». PT прямо пишет:
> Несоответствие между фактической обработкой трафика и отображением в интерфейсе: атака доходит до тестового backend или разрешается PT Cloud AF, но в консоли отображается как заблокированная, неопасная либо отсутствует в событиях.

## Векторы
- **Block vs Pass mismatch:**
  - AF вернул 403, но backend **всё равно исполнил** (запрос дошёл параллельно / через другую цепочку)
  - AF вернул 200, но в консоли «заблокировано»
- **Severity mismatch:**
  - AF помечает как `low`, а по факту — RCE
  - AF помечает как `high`, а по факту — безобидный запрос (false positive, менее интересно)
- **Missing events:**
  - Атака прошла, но в логе AF события нет
  - Событие есть, но привязано к другому tenant / domain
- **Duplicate / lost events:**
  - Одно событие на N запросов (потеря)
  - Событие есть, но с неверным payload'ом (AF залогировал не то, что дошло)
- **Agent vs Control plane mismatch:**
  - Agent заблокировал, control plane показывает «пропущено» (или наоборот)
  - Border и agent показывают разное
- **Caching mismatch:**
  - AF закэшировал «заблокировано», а backend исполнил
- **Async mismatch:**
  - AF отвечает 403, но запрос уходит в backend асинхронно

## Как валидировать (строго!)
1. **Backend исполнил:** тестовое приложение вернуло результат атаки (явный маркер: `id`, `uid=`, `/etc/passwd`, XSS сработал).
2. **AF в консоли:** скриншот события, где этот запрос:
   - помечен как «заблокировано», **но backend исполнил**
   - **отсутствует**, хотя backend исполнил
   - помечен как «неопасно», хотя backend исполнил
3. **Воспроизводимость:** повторить 2–3 раза, чтобы исключить race condition.

## Инструменты
- Burp (сравнение ответов AF и backend)
- Скриншоты консоли AF
- Логи тестового приложения (если доступны)
- `interactsh` (OOB-подтверждение, что запрос дошёл)

## Чек-лист
- [ ] Выбрать тестовый эндпоинт с явным маркером (RCE `id`, SQLi `version()`, path traversal `/etc/passwd`)
- [ ] Отправить атаку
- [ ] Зафиксировать ответ AF (403/200)
- [ ] Зафиксировать ответ backend (исполнил / нет)
- [ ] Открыть консоль AF → найти событие
- [ ] Сравнить: block/pass, severity, наличие события
- [ ] Повторить 2–3 раза
- [ ] Сделать скриншоты: запрос, ответ, событие в консоли
- [ ] В отчёте — явно показать mismatch

## Не делать
- Не путать «AF заблокировал, backend не исполнил» (это норма) с mismatch
- Не путать race condition с mismatch (повторить несколько раз)
- Не присылать отчёт без скриншота консоли AF + ответа backend
