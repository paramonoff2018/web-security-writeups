# Web Cache Deception (Обман веб-кэша) — Использование разделителей путей

**Платформа:** PortSwigger Web Security Academy
**Сложность:** Practitioner (Практикующий)
**Статус:** ✅ Solved

## 📌 Описание уязвимости
Уязвимость возникает, когда кэширующий сервер (CDN, прокси) и исходный сервер (бэкенд) по-разному интерпретируют символы в URL-пути. Если бэкенд использует определенный символ (например, `;` или `?`) как разделитель и обрывает на нем путь, а кэш — нет, возникает расхождение. 

Злоумышленник может использовать это, чтобы заставить кэш сохранить (закэшировать) конфиденциальный ответ (например, страницу профиля `/my-account`), выдав его за статический файл (например, `.js`), к которому жертва обратится через браузер.

## 🎯 Цель лабы
Получить API-ключ пользователя `carlos`, используя расхождения в парсинге URL между кэшем и бэкендом.

## 🛠️ Вектор атаки (Шаги)

### 1. Разведка и поиск расхождений (Fuzzing)
*   Логинимся как `wiener:peter` и перехватываем запрос `GET /my-account`.
*   Отправляем в **Intruder** запрос вида `/my-account§§abc` (без разделителя) с пейлоад-листом из лабы (символы и их URL-кодировки).
*   **Важно:** Отключаем `Payload encoding` в настройках Intruder, чтобы Burp не кодировал символы автоматически.
*   Находим символ, который бэкенд интерпретирует как разделитель (в этой лабе это `;`). Запрос `/my-account;abc` возвращает `200 OK` с ключом, а `/my-accountabc` возвращает `404`.

### 2. Проверка уязвимости кэша
*   В **Repeater** меняем путь на `/my-account;abc.js` и отправляем.
*   Смотрим заголовки: если появился `X-Cache: miss` (а при повторной отправке `X-Cache: hit`), значит, кэш видит расширение `.js`, применяет правило кэширования статики и сохраняет ответ, хотя бэкенд отдает динамическую страницу.

### 3. Эксплуатация
*   Используем **Exploit Server** для доставки полезной нагрузки жертве.
*   Тело эксплойта:
    ```html
    <script>document.location="https://YOUR-LAB-ID.web-security-academy.net/my-account;wcd.js"</script>

Критический нюанс (почему не получалось с первого раза): Если мы зайдем на эту ссылку в браузере до жертвы, кэш сохранит наш ответ (wiener).

Решение: ждем 40 секунд (время жизни кэша max-age=30), чтобы старый ответ «протух». Затем нажимаем Deliver exploit to victim и сразу же открываем ссылку в браузере. Бот (carlos) успевает первым, кэш сохраняет его ответ, и мы читаем чужой API-ключ.

🧠 Теория (Почему это работает)
Бэкенд (Apache/Tomcat): Использует ; как параметр матрицы (matrix parameter). Все, что идет после ;, он отбрасывает. Он видит путь /my-account и отдает профиль.

Кэш (CDN): Смотрит на расширение файла в конце URL. Видит .js и думает: «Ага, это статический скрипт, его нужно закэшировать и отдавать всем подряд».

🛡️ Как защититься (Mitigation)
Для кэша: Настроить правило, чтобы кэшировались только файлы из конкретной директории (например, /static/), а не по расширению в конце URL.

Для бэкенда: Добавлять заголовок Cache-Control: no-store, private для всех динамических страниц (особенно профилей и страниц с конфиденциальными данными).
